Cyberwarfare: What Open Models Change in Red Teaming

AI sovereignty is often discussed in terms of data centers, GPUs, and local hosting. This is obviously important. But that may not be where the most interesting change lies.

For a critical system, the question is not only what a model can do. We also need to know how far we can make it go.

This is particularly important for red teaming.

A system you have never attacked is a system you do not fully know

Consider a simple example: a situation center uses a model to summarize the previous day’s events every morning.

The system receives news reports, intelligence reports, internal notes, and various open sources. It analyzes and cross-references them, then produces a summary for human operators.

To test its robustness, we can feed it thousands of documents designed to trigger failures: contradictory information, fake sources, hidden instructions in the content, attempts to manipulate the context, or deliberately ambiguous information.

But a question quickly arises: who generates these attacks?

They can of course be written manually. The problem is scale. To explore enough variations, it becomes useful to use another model to automatically generate test scenarios.

This is where a less obvious problem appears.

A red team can use a model to automate the generation of adversarial scenarios. But that model is still subject to its own behavioral rules.

It may therefore refuse to produce certain scenarios because it considers them dangerous, illegal, or contrary to its usage policy.

For a general-purpose assistant, this behavior is normal.

For a model used by the red team as an attack generator, it is different: the refusal occurs precisely on the task for which the model is being used.

The problem is not that the red team would be unable to imagine the attack. It is that the tool responsible for generating the attacks can itself prevent certain categories of scenarios from entering the test campaign.

At scale, this can create a systematic bias in the test set: some attacks may be underrepresented, or completely absent, not because they are difficult to design, but because the model generating them refuses to produce them.

The interesting question: how far can we bend a model?

This is where open-weight models become particularly interesting.

The point is not simply to have an “uncensored” model.

The point is to be able to study what produces its behavior and experiment with that behavior.

With a closed API, the model’s behavioral rules are essentially a black box to the user. The provider controls the training, alignment mechanisms, safety policies, and how those mechanisms evolve.

With an open-weight model, part of that chain becomes accessible to experimentation.

We can then ask a different question:

What happens if we remove, modify, or attenuate some of the model’s behavioral constraints?

This is not simply a matter of prompting.

Research has shown that some refusal behaviors can be associated with internal representations of the model. In some cases, researchers have identified directions or representations associated with refusal and modified model behavior by intervening on those representations.

This opens up a particularly interesting avenue for red teaming.

Instead of simply looking for a model that refuses fewer requests, we can try to understand why it refuses, measure that behavior, and then study what changes when certain constraints are modified.

The model itself becomes an experimental object.

This is not simply about “removing censorship”

A simplistic conclusion should nevertheless be avoided.

Changing refusal behavior does not magically turn a model into an effective attack generator.

Safety mechanisms are intertwined with other model behaviors. A modification can produce side effects, degrade certain capabilities, or create unexpected behaviors.

And above all, a model that “accepts everything” is not necessarily a better red-team tool.

The interesting part is elsewhere.

We can imagine several versions of the same model:

  • the original model;
  • a version in which certain refusal behaviors have been modified;
  • a version adapted to a particular domain;
  • potentially several models exhibiting different behaviors.

We can then subject them to the same test suite and measure the differences.

Which scenarios are generated by every model?

Which are systematically refused?

Which only appear when certain behavioral constraints are modified?

Which new classes of scenarios become accessible?

And above all: what do these differences tell us about the blind spots of the system being tested?

This is where the idea becomes interesting.

The goal is not to build a model that disobeys every rule.

The goal is to have a model whose behavior can be studied, controlled, and adapted to the red-team function for which it is being used.

A red team does not have the same constraints as an operational system

There is a natural tension between these two uses.

A model used operationally generally needs to be cautious. It should avoid producing certain information, refuse certain requests, and follow safety rules.

A model used to test that same system needs to explore precisely the situations that the operational system is designed to prevent.

The two functions therefore pursue different objectives.

Using exactly the same model, with exactly the same constraints, for both tasks can lead to a strange situation: the model responsible for testing the defenses refuses to simulate some of the attacks that those defenses are supposed to withstand.

Separating the two functions makes it possible to approach the problem differently.

The operational model can retain its safeguards.

The model used by the red team can instead be treated as an experimental environment in which behaviors, constraints, and generation capabilities can be studied.

Measure the gap rather than look for a “better” model

One practical way to apply this idea would be to build a common test suite.

For example, scenarios could be generated by:

  • a strongly aligned commercial model;
  • another commercial model with a different policy;
  • an open-weight model;
  • a modified version of that open model.

All models receive the same information about the system being tested and are asked to produce adversarial scenarios.

The goal is not to determine which model is “the best.”

Instead, we want to measure the differences between the attack spaces they explore.

Which scenarios are produced by every model?

Which only appear with certain models?

Which categories are consistently underrepresented?

Which types of requests trigger refusals?

And what happens to this distribution when we modify the model’s behavioral constraints?

This comparison can become an auditing tool in its own right.

The gap between models is not necessarily a flaw to be corrected. It may be precisely what we are trying to measure.

Sovereignty as control

Local hosting is an obvious component of this sovereignty: data, models, and infrastructure remain under the organization’s control.

But it is only part of the issue.

The deeper question is the ability to control the model’s behavior.

If an organization depends entirely on an external API, it also depends on its provider for the model’s behavior, updates, usage limits, and safety policies.

With an open-weight model, it can instead build its own experimentation pipeline: compare several models, modify certain behavioral parameters, test the consequences, and retain the versions that correspond to its needs.

This capability is particularly important in an environment where models themselves become part of the attack and defense surface.

Four capabilities to maintain

To maintain this capability over time, four building blocks seem important.

1. The ability to experiment with models.

Being able to evaluate different open models and understand their behavior, particularly their refusal mechanisms and limitations.

2. The ability to modify them.

Being able to experiment with model behavior, compare different variants, and measure the effects of those modifications.

3. Automated red teaming.

Being able to regularly generate new adversarial scenarios and run them against the systems actually in use.

4. Measurement over time.

Models evolve. A test suite should therefore be rerun regularly to detect behavioral changes and new blind spots.

Local infrastructure remains necessary to retain control over data and execution, but here it becomes a means, not the primary objective.

A complementary capability, not a replacement

The goal is not to replace aligned models with models without safeguards.

A strongly aligned model can be perfectly appropriate for its operational role. Safety mechanisms are specifically designed to reduce certain forms of misuse and certain risks.

The problem appears when the same model is used for two different functions:

  • producing a safe operational response;
  • simulating an adversary that is specifically trying to bypass that safety.

These two objectives are not necessarily compatible.

Red teaming needs to explore behaviors that the operational system is specifically designed to prevent.

Using a different model for this task therefore makes it possible to separate the two functions.

Conclusion

The issue is ultimately not about choosing between a “censored” model and an “uncensored” model.

The more interesting question is:

how much control can an organization have over the behavior of the model it uses to test its own systems?

A commercial model can be excellent for an operational application while refusing to produce certain scenarios that would be useful in a red-team campaign.

An open-weight model offers another possibility: to stop treating model behavior as an immutable property, and instead treat it as something that can be studied, measured, compared, and, within certain limits, modified.

That may be one of the most important reasons open models are interesting for cybersecurity.

Not simply being able to run a model yourself.

But being able to ask it:

“What are your limits? Why are they there? What happens if I modify them? And what attacks do you see when I change the way you reason?”

For a critical system, this experimental capability can become part of its resilience.

A system that has never truly been tested under attack remains, to some extent, a system we do not know.
