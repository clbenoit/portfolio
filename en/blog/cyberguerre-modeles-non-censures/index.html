Cyberwarfare: What Open Models Change in Red Teaming

AI sovereignty is often discussed in terms of data centers, GPUs, and local hosting. This is obviously important. But there is another, less visible form of dependency: the behavioral constraints of the models we use.

For a critical system, the question is not only what a model can do. We also need to know what it is capable of producing when asked to test or attack the system it is supposed to help protect.

This is particularly important for red teaming.

A system you have never attacked is a system you do not fully know

Consider a simple example: a situation center uses a model to summarize the previous day’s events every morning.

The system receives news reports, intelligence reports, internal notes, and various open sources. It analyzes and cross-references them, then produces a summary for human operators.

To test its robustness, we can feed it thousands of documents designed to trigger failures: contradictory information, fake sources, hidden instructions in the content, attempts to manipulate the context, or deliberately ambiguous information.

But a question quickly arises: who generates these attacks?

They can of course be written manually. The problem is scale. To explore enough variations, it becomes useful to use another model to automatically generate test scenarios.

This is where a less obvious problem appears.

A red team can use a model to automate the generation of adversarial scenarios. But that model is still subject to its own behavioral rules.

It may therefore refuse to produce certain scenarios because it considers them dangerous, illegal, or contrary to its usage policy.

For a general-purpose assistant, this behavior is normal.

For a model used by the red team as an attack generator, it is different: the refusal occurs precisely on the task for which the model is being used.

The problem is not that the red team would be unable to imagine the attack. It is that the tool responsible for generating the attacks can itself prevent certain categories of scenarios from entering the test campaign.

At scale, this can create a systematic bias in the test set: some attacks may be underrepresented, or completely absent, not because they are difficult to design, but because the model generating them refuses to produce them.

Using multiple models to find blind spots

One possible response is to use multiple models.

The same battery of scenarios can be generated by several systems and the results compared. Each model has its own training data, behaviors, and constraints.

This already helps reduce the risk of relying on a single way of generating tests.

But it becomes particularly interesting when one of the models can be run locally and controlled by the organization using it.

Open-weight models make this possible.

They can be run on an organization’s own hardware, inside its own network, without sending test data to an external provider. They also make it possible to experiment more directly with the model itself, within the limits of its license and the available methods.

This does not mean that an open model is automatically better for red teaming.

It mainly means that the team has greater control over the tool used to build its tests.

De-censoring is not a magic solution

This point also needs to be stated precisely.

There are now methods for reducing or bypassing certain refusal behaviors in open-weight models. Research has shown, in particular, that in some models, some refusal behaviors can be associated with identifiable and modifiable internal representations.

This does not mean that there is a universal method for taking any model and instantly making it “uncensored.”

The techniques depend on the architecture, the model, its training, and the method being used. They can also alter or degrade other capabilities of the model.

The real value is therefore not to build a model that “accepts everything.”

The value is having an additional experimental capability: being able to study how model behavior changes when certain constraints are modified, and then measure the consequences.

For a critical system, that capability is already valuable.

Sovereignty is not limited to hosting

AI sovereignty is often reduced to an infrastructure question: where are the servers? Where is the data stored? Who owns the GPUs?

These questions are essential, but they are not sufficient.

If a system depends entirely on a foreign API, the organization also depends on its provider for the model’s behavior, updates, usage limits, and safety policies.

That dependency may be perfectly acceptable for some use cases.

It becomes more problematic when the goal is to build an auditing capability that is independent of the model provider.

Open models offer an alternative: a model that can be run on your own hardware, inside your own network, with an execution stack that you control.

The benefit is not only data confidentiality.

It is also the ability to build your own evaluation methods and evolve them independently of the model provider.

Measure the gap rather than look for a “better” model

One practical way to apply this idea would be to build a common test suite.

For example, scenarios could be generated by:

  • a strongly aligned commercial model;
  • another commercial model with a different policy;
  • an open-weight model running locally;
  • potentially a modified version of the open model.

All models would then receive the same information about the system being tested and be asked to produce attack scenarios.

The goal is not to determine which model is “the best.”

Instead, we want to measure the differences between the scenarios they explore.

Which scenarios are produced by every model?

Which only appear with certain models?

Which categories are consistently underrepresented?

Which types of requests trigger refusals?

And most importantly: which classes of scenarios appear when using a model with different behavioral constraints?

This comparison can become an auditing tool in its own right.

The gap between models is not necessarily a flaw to be corrected. It may be precisely what we are trying to measure.

Four capabilities to maintain

For an organization that wants to maintain this capability over time, I see four important building blocks.

1. A local execution capability.

Having the hardware, open models, and infrastructure required to run models without systematically depending on an external API.

2. A capability for experimentation with models.

Being able to evaluate, adapt, and compare different open models, including their refusal behaviors and limitations.

3. Automated red teaming.

Being able to regularly generate new attack scenarios and run them against the systems actually in use.

4. Measurement over time.

Models change. Their policies change, their weights change, and their alignment methods change. A test suite should therefore be rerun regularly rather than conducted only once.

A complementary capability, not a replacement

The goal is not to replace aligned models with models without safeguards.

A strongly aligned model can be perfectly appropriate for its operational role. Safety mechanisms are specifically designed to reduce certain forms of misuse and certain risks.

The problem appears when the same model is used for two different functions:

  • producing a safe operational response;
  • simulating an adversary that is specifically trying to bypass that safety.

These two objectives are not necessarily compatible.

Red teaming needs to explore behaviors that the operational system is specifically designed to prevent.

Using a different model for this task therefore makes it possible to separate the two functions.

Conclusion

The issue is ultimately not about choosing between a “censored” model and an “uncensored” model.

For a critical system, it is more useful to have multiple perspectives capable of testing its limits.

A commercial model can be excellent for an operational application while being less suited to certain red-teaming tasks. An open model can provide another perspective, particularly because its environment and some of its characteristics can be controlled by the organization using it.

AI sovereignty therefore does not consist solely of owning the GPUs capable of running a model.

It also means retaining the ability to test, compare, and modify your AI tools without being entirely dependent on their provider.

In a critical environment, this capability directly contributes to system resilience.

A system that has never truly been tested under attack remains, to some extent, a system we do not know.
